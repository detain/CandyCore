## 1. Spec claim — the discard (CONFIRMED)

`ScriptHook::EXIT_ALLOW` returns `HookResult::allow($output)` at `src/Hooks/ScriptHook.php:642` — the
hook's stdout is carried in the result's `->message`. But `HookRegistry::executeHooks()` ends:

```php
return $modified ?? $inertRewrite ?? HookResult::allow();
```

at `src/Hooks/HookRegistry.php:428` — rebuilding a permitting verdict with an **empty** message, so the
stdout is thrown away. `src/Hooks/ScriptHook.php:631-641` documents this verbatim in a doc-comment: on
the live path it "goes NOWHERE", and both gates (`Runtime::gate()`, `Chat::gateToolCall()`) interpolate
`$hookResult->message` only into `"Hook denied: …"`. Confirmed at those exact lines.

## 2. `HookResult` shape (a clean 4th field)

`src/Hooks/HookResult.php:32-36` carries exactly three fields — `public string $action`,
`public string $message`, `public ?string $modifiedInput = null` — and **no `additionalContext`
anywhere**. Repo-wide absence confirmed: **0** hits for `additionalContext` / `additional_context` in
either `src/` or `tests/` (and **0** hits for the word `spillover` in `src/`). So `additionalContext` is
a clean 4th field: add it as a **defaulted promoted `readonly` ctor param** (`public string
$additionalContext = ''`) so all factory arms and every existing `new self(...)` call site stay valid.

## 3. Internal rebuild-drop-points (the field dies here — ALL must be threaded)

Even after `:428` is fixed, a plain permitting result is dropped at four internal points; the producer
must thread the field through **all four** or it never reaches a consumer:

- **(a) `scan()`.** Returns a 3-tuple `@return array{0:?HookResult,1:?HookResult,2:?HookResult}` at
  `src/Hooks/HookRegistry.php:662-665`; a plain permitting result exits iteration **unstored** at
  `:767-769` (`if ($proposal === null) { continue; }`). The `executeHooks():342` destructure
  `[$blocking, $rewrite, $inertRewrite] = $this->scan(...)` matches that tuple. A widened tuple (or an
  out-slot) is required to collect `additionalContext` across hooks.
- **(b) the ASK rebuild** at `:418` — `HookResult::ask($blocking->message, $modified?->modifiedInput)`
  is 2-arg and drops any collected context.
- **(c) the allow/settled arm** at `:428` — the empty-message rebuild from §1.
- **(d) `HookManager::resolveAsk()`** at `src/Hooks/HookManager.php:180-201` re-materialises the settled
  verdict **three ways** (`deny` / `allow` / `modify`); all three must carry the field so an approved
  ASK does not drop it.

## 4. Consumer trace (§1.10) — producer-only wiring would be dead code

`executeHooks()` has **exactly two callers**: `HookManager::preToolUse()`
(`src/Hooks/HookManager.php:158-160`) and `postToolUse()` (`:207-209`). Those resolve to **four
production sites**:

| Site | Path | Reads `additionalContext`? |
|---|---|---|
| `src/Runtime.php:1902` | `gate()` (→ `preToolUse`) | reads `->message` **only** on the deny branch `:1930-1931` |
| `src/Runtime.php:2009` | `settle()` (→ `postToolUse`) | **DISCARDED entirely** — a bare statement, return value unassigned |
| `src/Chat.php:3575` | `gateToolCall()` (→ `preToolUse`) | deny branch only `:3590-3593` |
| `src/Chat.php:3664` | `applyPostToolUse()` (`:3661-3668`) | **DISCARDED** — return value unassigned |

`applyPreHooks()` funnels to `preToolUse()` but is constructed by tests only. `HookDispatcher` (which
*does* carry the message) is constructed by **nothing** in `src/` (tests only) — not a live consumer.
**Therefore producer-only wiring = a brand-new dead field**, which §1.10 forbids shipping.

**SUPERVISOR RULING R-1 (2026-09-06): wire BOTH model-visible consumers** — `Runtime::settle()` via its
existing blessed `self::annotate()` seam (`src/Runtime.php:2011`, `:2024`), and
`Chat::applyPostToolUse()` — so the field is genuinely READ on the live tool-result path. This
explicitly **clears the `src/Chat.php` collision row for P7.S1**.

## 5. No spillover-to-file precedent

`src/Tools/Concerns/TruncatesOutput.php` (731 lines) truncates by **bytes** (caps 65536 / 16384 / 120),
**DROPS** overflow with an inline `PARTIAL` marker naming byte counts (`truncationMarker()`
`:273-281`), has **zero** filesystem I/O, and every method is `private`. The only `src/` file writers are
`src/Support/ToolIpcFiles` — `reserve()` `:225`, `write()` `:246` (0600-via-`umask(0o077)` + atomic
`rename`), `discard()` `:267` — and **every** caller is a fork/IPC handoff whose file is DELETED after
read and swept hourly (`STALE_AFTER_SECONDS = 3600`; sweep wired `src/Cli/Bootstrap.php:2124`, `:2255`).
None returns a path the model reads later. The word "spillover" is 0 hits in `src/`.

**So P7.S1's retained-overflow file is genuinely new.** **SUPERVISOR RULING R-2:** build a *retained*
path (ToolIpcFiles-style 0600 + atomic rename, but **NOT** discarded — lifetime tied to the
session/tool-result, **not** the 1h IPC sweep).

**OPEN RISK carried into the brief:** prove the hourly sweep / `discard()` / partial-suffix cleanup
cannot delete the file before its consumer reads it — else **HALT**. (Step brief §Hard constraints,
item 6.)

## 6. Units conflict → ORCHESTRATOR RULING R-3: cap is 10,000 **BYTES**

The plan text says "10,000 **characters**", but the whole subsystem is byte-denominated and
`ScriptHook::clip()` (`src/Hooks/ScriptHook.php:863-865`) states byte-boundary cutting is *deliberate*
("arbitrary program output, not guaranteed UTF-8"). Use `mb_strcut(..., 'UTF-8')` per the
`TruncatesOutput` idiom, expose the cap as a `public const` **in bytes** (e.g.
`MAX_ADDITIONAL_CONTEXT_BYTES = 10000`), and **avoid** the `$maxBytes <= 0` "no cap" sentinel —
`TruncatesOutput.php:141-142` documents it and `:367-379` records that misusing it silently disabled the
bound twice (Glob returned **1,091,833** bytes against a 65,536 cap).
